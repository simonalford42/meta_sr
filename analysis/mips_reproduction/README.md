# MIPS partial reproduction

Date: 2026-08-24

Paper: [Opening the AI black box: program synthesis via mechanistic
interpretability](https://arxiv.org/abs/2402.05110) (Michaud et al., 2024)

Official repository:
[ejmichaud/neural-verification](https://github.com/ejmichaud/neural-verification)

## Verdict

The pretrained-model MIPS extraction pipeline works on the three tasks tested:

- Binary Addition, the paper's flagship ripple-carry-adder example;
- Current Number / `rnn_identity_numerical`;
- Prev3 / `rnn_prev3_numerical`.

For every task, the regenerated Python program was byte-for-byte identical to
the program committed by the authors on their `pipeline` branch. Each program
also achieved 100% sequence and element accuracy on all 900,000 training and
100,000 held-out sequences generated by the authors' task script.

This is a successful **partial reproduction of program extraction from the
authors' pretrained RNNs**. It is not a reproduction of the preceding RNN
architecture search/training, and the repository as published cannot reproduce
the full 32/62 headline result without repairs and missing artifacts.

|---|---|---:|---:|---:|---:|---:|
| Binary Addition | `bit_addition` | Boolean regression | 2 | yes | 900,000/900,000 sequences | 100,000/100,000 sequences |

## Compute used

The successful task runs used roughly 0.05 CPU-hours in total (dataset
generation, integer autoencoding, regression, and full validation), with less
than 1 GB peak resident memory. Approximate wall times were:

| Task | Dataset | Integer autoencoder | Regression + full validation |
|---|---:|---:|---:|
| Current Number | 1.8 s | 10.7 s | 3.8 s |
| Prev3 | 1.7 s | 18.5 s | 3.3 s |
| Binary Addition | 2.7 s | 27.5 s | 4.9 s |

The binary-addition autoencoder used parallel BLAS and consumed about 119 CPU
seconds during its 27.5 seconds of wall time. This is still far below the
one-CPU-day limit.

## Reproduction procedure and deviations

The upstream README's four-step procedure does not work literally. The working
subset procedure was:

1. Clone the official repository and check out the pinned `pipeline` commit.
2. Download and unpack the linked `first_paper` archive under
   `regression/tasks/`.
3. Run each downloaded `create_dataset.py`, which creates one million sequences
   with the authors' seed and a 90/10 train/test split.
4. Link the generated dataset and the archive's `model_config.pt` and
   `model_perfect.pt` into the corresponding top-level `tasks/<task>/`
   directory. This is necessary because `auto_encode_RNN.py` reads from
   `../tasks/`, although the README says to place the archive at
   `regression/tasks/`.
5. From `regression/`, run:

   ```bash
   python auto_encode_RNN.py --task <task> --device cpu
   ```

6. Execute the relevant upstream notebook function and validate the generated
   program using:

   ```bash
   python scripts/reproduce_mips_subset.py \
       --repo /path/to/neural-verification \
       --task <task> \
       --method <linear-or-boolean> \
       --output-dir analysis/mips_reproduction/<task>
   ```

The notebooks' own success check is weak: `get_data()` defaults to 1,000
training sequences and the generated verifier checks only 1% of those, i.e. 10
training examples. The helper therefore additionally checks all one million
train/test sequences and reports the two splits separately.

## Why the full 32/62 table is not currently one-command reproducible

1. `main` contains README instructions for `regression/run.ipynb`, but the
   entire `regression/` directory is absent from `main`. The code is split over
   unmerged branches.
2. The linked archive contains 75 task directories and 70 raw
   `model_perfect.pt` checkpoints, but no `data.pt` files and no hammered model
   checkpoints. The paper benchmark contains 62 tasks.
3. The only `run.ipynb` hardcodes `ckpts = ['models_hammered']`, but neither the
   repository nor the linked archive contains the required
   `models_hammered/<task>/post_hammer_retrain_model_{config,best}.pt` files.
   The paper says normalization sometimes makes the difference between success
   and failure, so substituting the raw checkpoints is not guaranteed to
   reproduce 32/62.
4. `run.ipynb` enumerates every directory under the repository's top-level
   `tasks/` (147 on its branch), rather than the 62 entries in
   `first_paper_final.yaml`.
5. The driver uses `DataFrame.append`, which was removed in pandas 2.0. It needs
   a pandas <2 environment or a small `pd.concat` update.
6. There is no requirements file or locked environment for the extraction
   pipeline. Symbolic regression compiles a C++ executable at runtime and needs
   a working `g++` toolchain.

## What a full reproduction would take

For a **full pretrained-checkpoint reproduction** of Table 1:

1. Obtain the exact hammered checkpoints used in the paper from the authors,
   or deterministically regenerate them with the normalizer pipeline.
2. Consolidate the code from the unmerged branches and pin an environment.
3. Repair the archive/task paths, select exactly the 62 YAML tasks, replace the
   removed pandas API, and add checked subprocess failures.
4. Generate all 62 datasets, run integer/Boolean autoencoding and all three
   regression fallbacks, and independently evaluate each synthesized program
   on the full held-out split.
5. Compare the resulting success vector task-by-task with Table 1, not merely
   the aggregate count of 32.

Based on the three runs here, extraction itself is small enough that the 62-task
pretrained reproduction could plausibly fit within one CPU-day after those
engineering and artifact issues are resolved. The missing hammered checkpoints,
not raw compute, are the present blocker to an exact headline reproduction.

For a **fully end-to-end reproduction from scratch**, the cost is much larger.
The paper trains five seeds for every candidate architecture for 10,000 or
20,000 steps, performs an upward sweep and then binary search independently for
each of 62 tasks, and subsequently normalizes/retrains the selected networks.
The upstream implementation launches this work through SLURM. CPU-only
end-to-end reproduction is not realistic within one CPU-day; it would require a
GPU/SLURM campaign and likely many GPU-days, with the exact total depending on
how many architecture candidates each task needs.

## Full raw-checkpoint run

The full-run harness is
[`scripts/reproduce_mips_all.py`](../../scripts/reproduce_mips_all.py). It pins
the benchmark and extraction commits, constructs an isolated node-local
workspace for each task, applies the authors' linear/Boolean/symbolic fallback
order, and independently validates any notebook success against the complete
training and held-out datasets. Isolation is necessary because the notebooks
otherwise overwrite a shared generated program and compile a shared C++
executable.

The harness records all 62 benchmark entries. Consistent with the authors'
driver, the five tasks with hidden dimension above 10 are recorded as protocol
skips before dataset generation; the remaining 57 receive extraction attempts.
Each processed task runs with one CPU and a 3,600-second child-process timeout,
so a nonterminating symbolic search is killed together with its subprocesses
and recorded as `timeout`.

The ready-to-uncomment submission block is at the top of `submit_jobs.sh`. It
uses a 62-element array limited to 12 concurrent workers, 8 GB per worker, a
1:10 scheduler limit, and a dependent aggregation job. Results are written to
the ignored directory `outputs/mips_reproduction_all/`; `summary.json`,
`summary.csv`, and `SUMMARY.md` are generated after the array finishes.
